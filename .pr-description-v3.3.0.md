## What this PR enables

The `hermes-agent-a2a` plugin has grown into a "god module" — `server.py` was 2,318 lines handling HTTP routing, A2A protocol tasks, webhook delivery, push notifications, SSE streaming, and tool handlers all in one file. This release extracts three transport modules into small, focused files:

- `telegram_float.py` — the Telegram delivery transport. The "float" is the user-facing delivery path: a post-handler side effect that surfaces results to the human via Telegram.
- `a2a_direct.py` — single-shot JSON-RPC call to a remote A2A agent (the "direct" path: when one agent calls another without going through the local webhook).
- `webhook_delivery.py` — HMAC-signed POST to the local agent webhook with retry-with-backoff and SSRF guard (the "webhook" path: the production cross-agent delivery).

Each transport is now a small, focused module with no internal dependencies. The caller passes a target URL and credentials; the transport doesn't know who's using it.

**Why it matters:**
- **Testability:** Transport modules can be tested in isolation, without spinning up the full HTTP server. New `tests/test_a2a_direct.py`, `tests/test_webhook_delivery.py`, and `tests/test_tool_handlers_stays.py` cover the *module-internal* surface (env vars, response shapes, error-to-dict conversion, retry formulas, signature headers). The existing `tests/test_current_tools.py` continues to cover the *call site* (server.py uses the extracted modules). The two test files are complementary, not duplicative.
- **Reusability:** Future transports (e.g. for new A2A delivery modes, or for non-Telegram float channels like email or Signal) can follow the same pattern. The transport module's signature is `module.action(...)` — module name is the transport, function name is the action.
- **Audit chain:** The 5 v3.3 commits (Tasks 3-7) are each readable on their own, with the v3 SPEC and refactor discipline references in each commit message. The `a2a-review-20260602` review trail is preserved. Reviewers can `git log` the v3.3 lineage and follow the audit chain without squashing.

## v3.3 deviations (3) with rationale

1. **Naming: `webhook_delivery.trigger` / `trigger_async`, not `deliver`.** The v3 SPEC naming decision (Q1 final, 2026-06-02) framed this as `webhook_delivery.deliver(task_id)`. The original function names are `trigger` — they trigger a webhook delivery. **The original names are preserved to keep the extraction a pure code-organization refactor with no public-API churn.** The `deliver` rename can land in a follow-up commit if the naming is revisited. See Task 5 commit `1796c11`.

2. **Lazy-import pattern (3 places).** The extraction introduced a circular dependency: `webhook_delivery` needs `_validate_webhook_host` from `server.py` (used by `_push_notifications_capability`), but `server.py` imports `webhook_delivery`. **Solved with lazy in-function imports** — `from .server import _validate_webhook_host` inside the function body, not at module level. Same pattern for `a2a_spec.tasks.build_task_send_payload` in `a2a_direct.call` (avoids pulling `a2a_spec` onto the hot path) and for `a2a_direct.call` / `call_async` in `webhook_delivery.trigger` / `trigger_async` (lazy in the `use_direct_a2a` branch). The pattern is load-bearing for circular dependencies and hot-path performance. See Task 4 commit `5534b5f` and Task 5 commit `1796c11`.

3. **Test split: integration tests vs module-internal tests.** The existing `tests/test_current_tools.py` covers the *call site* — server.py uses the extracted modules. The new `tests/test_a2a_direct.py`, `tests/test_webhook_delivery.py`, and `tests/test_tool_handlers_stays.py` cover the *module-internal surface* — the extracted modules' own behavior. **The two test files are complementary, not duplicative.** The discipline: when extracting a function, the existing integration test file covers the call site, the new module-internal test file covers the extracted module's surface. The discipline is the split. See Task 6 commit `69009a6`.

**Bandit findings — flagged but resolved on review:**

- B107 `hardcoded_password_default` (2 instances): the `auth_token: str = ""` default-parameter declarations. The empty string is the documented "no token" default, not a hardcoded password. The B107 default-value heuristic flags any `param=""` style default; the actual code passes the value through to the request, never using it as a credential lookup.
- B310 `urlopen-permitted-schemes` (4 instances): Bandit flags `urlopen` calls as auditable. The audit is performed in this PR: the URL is constructed from a validated host or a caller-supplied target, with no SSRF surface. The webhook path validates `A2A_WEBHOOK_HOST` against the SSRF guard (`_validate_webhook_host`) before building the URL; the direct-A2A path takes a caller-supplied `target_url` that the caller is responsible for validating.
